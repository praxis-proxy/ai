# Anthropic Schema Conformance Design

## Context

Issue #416 identifies Anthropic response bodies generated by Praxis AI that
do not match the canonical Anthropic Messages and error response schemas.
The affected paths are:

- non-streaming Chat Completions-to-Messages response translation;
- `message_start` and `message_delta` usage objects in translated SSE;
- local rejections from Anthropic classification, validation, and request
  translation; and
- upstream 4xx and 5xx responses returned by Chat Completions-compatible
  backends.

The current emitters construct JSON independently. Some omit required
nullable properties, two interpolate diagnostic text into JSON manually,
and the response translator deliberately passes upstream error bodies
through unchanged.

## Goals

- Emit schema-complete Anthropic `Message`, `Usage`, `MessageDeltaUsage`,
  and `ErrorResponse` objects.
- Serialize all diagnostic text through Serde.
- Translate pre-stream upstream 4xx and 5xx responses into Anthropic error
  envelopes while preserving the HTTP status.
- Keep successful SSE responses incremental.
- Centralize Anthropic wire-shape construction so streaming and
  non-streaming responses cannot drift independently.
- Avoid unnecessary cloning or full-body buffering.

## Non-goals

- No Praxis core changes.
- No changes to Anthropic request translation semantics.
- No translation of errors that occur inside an already-started HTTP 200
  SSE stream.
- No attempt to synthesize an Anthropic request ID. Locally generated
  errors use `request_id: null`.
- No broad refactor of content-block or stop-reason translation.

## Architecture

Add a private `apis/src/anthropic/wire.rs` module containing Serde-backed
wire types and constructors shared by the Anthropic filters:

- `MessageResponse` for complete non-streaming Messages responses;
- `MessageUsage` for full response and `message_start` usage;
- `MessageDeltaUsage` for terminal streaming deltas; and
- `ErrorResponse` plus helpers for JSON bodies and `Rejection` values.

Required nullable fields are represented with `Option` and are serialized
without `skip_serializing_if`, so `None` becomes an explicit JSON `null`.
Strings are borrowed where practical. Content blocks and the generated
message ID remain owned because response translation already constructs
them.

The module is private to the Anthropic implementation and adds no public
API or dependency.

## Wire Shapes

### Message and full usage

Translated non-streaming messages include:

- `id`, `content`, `model`, `role`, `stop_reason`, `stop_sequence`, and
  `type`;
- typed text blocks with `citations: null`;
- typed tool-use blocks with `caller: {"type":"direct"}`;
- `container: null`;
- `stop_details: null`; and
- a complete `usage` object.

Full usage includes:

- `input_tokens` and `output_tokens`;
- `cache_read_input_tokens` when the upstream reports cached prompt
  tokens, otherwise `null`; and
- `cache_creation`, `cache_creation_input_tokens`, `inference_geo`,
  `server_tool_use`, and `service_tier` as `null` because Chat Completions
  does not provide compatible values.

`output_tokens_details` is omitted. It is optional in Anthropic's current
API but absent from the compatibility schema targeted by this change.

The existing subtraction of cached tokens from `input_tokens` remains
unchanged.

### Streaming usage

`message_start.usage` uses the full usage type with zero input and output
tokens. `message_delta.usage` uses its own schema, with cumulative
`output_tokens` and explicit null values for
`cache_creation_input_tokens`, `cache_read_input_tokens`, `input_tokens`,
and `server_tool_use`. Both usage shapes omit `output_tokens_details`.

No streaming chunk or provider payload is cloned solely for schema
completion.

### Errors

Every locally generated Anthropic error uses:

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "..."
  },
  "request_id": null
}
```

The shared constructor accepts borrowed error type, message, and optional
request ID values and serializes them with Serde. A constant,
schema-complete fallback body is used only if serialization unexpectedly
fails.

## Response Data Flow

Praxis runs response filters in reverse configuration order. In the
existing example pipeline, `anthropic_stream_events` therefore sees a
successful SSE response before `anthropic_to_openai`.

`anthropic_to_openai` selects buffering as follows:

- successful non-streaming response: buffer and translate as today;
- successful streaming response: do not buffer;
- any 4xx or 5xx response: buffer, regardless of the request's `stream`
  value; and
- other response classes: preserve the existing pass-through behavior.

The streaming filter continues to arm only for successful
`text/event-stream` responses. A 4xx or 5xx JSON or SSE response is left
unarmed, then buffered and normalized by `anthropic_to_openai`. This
matches Anthropic's pre-stream error behavior and does not change
incremental successful streaming.

After a buffered error body completes, the translator:

1. extracts `error.message`, falling back to a top-level `message` or a
   status-based generic message;
2. preserves an upstream error type when it is a documented Anthropic
   type, or when a canonical top-level `"type": "error"` discriminator
   identifies a forward-compatible Anthropic error envelope;
3. otherwise maps the HTTP status to the closest Anthropic type;
4. copies `request_id` from the body or the `request-id` response header,
   falling back to `x-request-id`, and exposes the canonical `request-id`
   response header when available;
5. preserves the upstream HTTP status; and
6. sets the content type to JSON and removes stale `Content-Length`,
   `Content-Encoding`, `Content-Range`, and `ETag` representation metadata
   before buffering so clients interpret the transformed body correctly.

The request transformation removes `Accept-Encoding` because Praxis does not
decode upstream response bodies. If an upstream still returns an encoded or
partial successful representation, Praxis passes that response through
unchanged instead of attempting to parse and corrupt it.

The status mapping covers Anthropic's documented types:

- 400 and other unmapped 4xx: `invalid_request_error`;
- 401: `authentication_error`;
- 402: `billing_error`;
- 403: `permission_error`;
- 404: `not_found_error`;
- 409: `conflict_error`;
- 413: `request_too_large`;
- 429: `rate_limit_error`;
- 504: `timeout_error`;
- 529: `overloaded_error`; and
- other 5xx: `api_error`.

Unknown upstream body text is not reflected verbatim.

## Local Rejection Integration

The following call sites use the shared rejection constructor:

- `anthropic/messages_format`;
- `anthropic/validate`; and
- request transformation failures in `anthropic/to_openai`.

Their existing status codes and filter control flow remain unchanged.
Replacing manual formatting also makes quotes, backslashes, newlines, and
control characters safe.

## Testing

Implementation follows test-first development.

Unit coverage will verify:

- exact presence and nullability of all non-streaming `Message` and
  `Usage` fields;
- exact presence and nullability of streaming start and delta usage
  fields, including omission of `output_tokens_details`;
- complete local error envelopes;
- diagnostic text round-trips through JSON escaping;
- preservation of compatible upstream error types and request IDs;
- status-based mapping for incompatible upstream error types;
- buffering decisions for successful streaming, successful
  non-streaming, and 4xx/5xx responses; and
- safe fallback behavior for empty, malformed, or non-object upstream
  error bodies.

Functional coverage through
`examples/configs/anthropic/messages-to-openai.yaml` will verify:

- a schema-complete successful translated response;
- a normalized upstream error for a non-streaming request; and
- the same pre-stream error behavior when the original Anthropic request
  sets `stream: true`.

Targeted crate tests run first, followed by formatting, linting, the full
workspace test suite, and documentation checks before publication.

## Compatibility and Performance

This is an additive response-shape correction. Existing populated fields
retain their values, while previously absent nullable fields become
explicitly null.

Successful SSE remains `BodyMode::Stream`. Only responses that already
require whole-body translation, plus 4xx/5xx error bodies bounded by the
existing `max_body_bytes` setting, use `StreamBuffer`.

The design performs one JSON parse and one serialization for a buffered
response. It does not add clones of request bodies, response bodies,
streaming chunks, or provider payloads.
